### 2. hot 排序 SQL 恒零 bug（commit 336a460，已部署）——重要存量 bug
- **根因**：`gravity_sql_expression` 分子写成 `ai_score/10.0 - 1`，对 0-10 分恒 ≤0 → 全表 rank=0 → ORDER BY 落到次级 `created_at DESC`。即**hot 排序自上线以来一直等价于 latest**，gravity 衰减从未生效（生产实测 rank_sql 全为 0E-20 证实）。test_ranking.py 只断言字符串包含列名，没测语义，所以一直没发现。
- **修复**：分子改 `ai_score - 1`，与 Python 版 calculate_ranking_score 对齐。修复后线上排序严格 rank 降序（1.408→1.230→1.069…），高分+新近新闻真正靠前。
- 昨天"事件卡被 gravity 衰减埋掉"的诊断要修正：真实原因是 hot≈latest，7h+ 旧事件被新条目纯按时间挤下去。

### 6b. 事件差异化衰减（commit 1c03077，已上线验证）——用户反馈"前端没有展示"的最终解
- 排查链：事件卡存在但排不出首页——约旦卡 #21 刚好在 PAGE_SIZE=20 之外；15信源车企卡最新子报道 14h，rank 仅 0.048（1.8 次方衰减分母 147）。**加分补偿不了指数衰减**。

### 12. 决策：五维评分暂缓（2026-08-02）
- 用户问"五维评分有用吗"，给出的建议是**不做**。理由：①LLM 原子分是假精确（四维高度相关=同一判断切五刀，权重拍脑袋无法校准）；②结构化简报上线不满一天，must_know 选得不准没有证据，属过度设计；③成本高（合成输出+4 字段/存量回落/程序预分层与 LLM 权责模糊）。
- 替代方案（如需要更强候选秩序）：change_type 权重 → ai_score × ln(source_count+1) → 时效，零新字段覆盖 80% 效果（ai_score=影响力、change_type=增量、source_count=可信度、status=紧迫性）。
- 重启条件：出现真实消费者（推送阈值/个性化 relevance）或观察一两周后发现 must_know 确实选得烂。

### 20. Bug：无新事件时丢掉持续事件 + news_count 误写为 0（commit d5fce51，已部署+实测）
- **现象**：`generate_digest` 在 `if not events:` 时直接 `return` 并存 `schema_version=1 / news_count=0`，导致：①上一份 developing 状态的持续事件（已算好的 `ongoing_updates`）被丢弃，用户看不到；②即使本时段收录很多报道，news_count 也被错误清零。
- **修复**（backend/app/services/digest_service.py）：拆成「有事件=调 LLM 完整简报(原逻辑)」/「无新事件但有 ongoing/quiet=不调 LLM、程序生成 v2 简报且填入真实 ongoing/quiet」/「真正无=生成 v2 空简报」三种情况。统一用真实 `article_count` 作为 `news_count`（不再写 0），`schema_version=2`，并仍调用 `_save_event_links(..., [], prev_links)` 保留下一份简报的持续事件对比基线。
- **实测**：容器内 mock 注入「无事件但 ongoing/quiet 各 1 条」场景跑 `generate_digest`，结果 `status=ok / schema_version=2 / news_count=42(真实) / ongoing_updates 与 quiet_topics 均保留真实条目`，确认修复生效（部署前先 docker cp 改后文件进容器跑通，再 git 提交 + 全量重建 web）。
- 注意：用户给的 case-2 JSON 模板里 `ongoing_updates/quiet_topics` 写成 `[]`，但与其 bug 描述（"持续事件会被丢掉"）及触发条件矛盾，已按修复意图填入真实列表；若用户确实想清空这两者需再确认。
